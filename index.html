Rebuilding a network-operations portal around how ops teams work

Company
Verizon, via Incedo
Role
UX, UI design, front end
Stack
React, TypeScript, MUI
Result
25% less duplicated UI code
EngineeringCustomersProduct

The portal had grown one screen at a time. I talked with the ops users, redesigned the main workflows directly in code, and rebuilt the UI on a shared component library, so problems stand out at a glance and every page works the same way.

The problem

Similar views had been built several times with slightly different patterns. Users had to relearn each page, finding things took too many clicks, and engineers fixed the same bug in several places.

What I did

I talked directly with ops users to understand their daily workflows and the pain points they reported. Then I designed in code, prototyping flows and layouts in React so users could react to real screens. I demoed working builds and changed the design based on their feedback.

Design decisions

  • Status first. A colored dot and short label on every row, so problems stand out before you read.
  • Summary before detail. Three key numbers on top, the list below, sorted by urgency.
  • Fewer steps. Search and filters on the same screen as the list.
  • One pattern everywhere. The same navigation and table behavior on every page.

A shared component library

I built the UI on Material UI with one theme for color, type and spacing, and a small set of components on top. Status colors are reserved for state; the accent is only for actions. Every new page now looks and behaves the same without extra work.

After launch

I kept listening after release. Users found some things hard to find, so I reworked navigation and filters. Some screens showed too much at once, so I simplified them. A few views were slow, so I fixed them.

Results

  • 25% less duplicated UI code.
  • Fewer clicks and screens for common tasks.
  • Fewer bugs and support tickets, and positive feedback from users and the client.
  • Best Deliverables recognition.

What I learned

Showing users a working build gets better feedback than describing it. And launch is the middle of the project: the biggest improvements came from what users told me after release.

Mapping thousands of network sites with WebGL, and showing where data is stuck

Company
Verizon, via Incedo
Role
Design and build
Stack
WebGL, React, GeoServer, Kafka
Result
20% better reliability
EngineeringCustomersProduct

Ops teams needed to see where things were happening, not read a list. I built map views that render large numbers of site markers smoothly with WebGL, GIS diff maps that show what changed between data loads, and a live view of how data moves through the system.

The map

The land is a quiet dot grid so the markers carry the color. Color only means state: green healthy, amber warning, red pulsing for trouble. One toggle switches from live status to what changed.

Behind the map

I integrated GeoServer for the GIS diff maps and wrote Python scripts that ingest and standardize county boundary data from several sources.

Live data flow

Kafka metrics lived in tables and graphs, so the whole path a message takes was hard to see. I built reusable React components that draw topic flows in real time. Moving lines mean live data; a stalled path stops moving and turns red.

Results

Together with Grafana dashboards for lag, throughput and broker health, faster root-cause diagnosis improved system reliability by 20%.

What I learned

On a map, color is the loudest thing on screen, so it should mean only one thing. And performance is part of the design: if panning stutters, people stop exploring.

Turning a reporting dashboard into an assistant that suggests what to do next

Company
Verizon, via Incedo
Role
Concept, design, build, demo
Stack
Gemini API, React
Audience
Client stakeholders
EngineeringCustomersProduct

The platform showed plenty of data but left the diagnosis to people. When something broke, operators pieced together the cause from several dashboards. I designed and built a working GenAI prototype that explains the likely cause and suggests next steps, and presented it directly to the client.

How I design AI into an interface

AI answers can be slow, wrong or unavailable, and the interface has to make that fine. I follow a few rules:

  • Show where it came from. Every answer lists its sources so people can check it.
  • Say how sure it is. A confidence bar sets expectations before someone acts.
  • Stream, don't spin. Text appears as it's written.
  • Keep people in control. The assistant suggests; the operator acts, and can stop it.
  • Fail gracefully. If AI isn't available, fall back to something useful. The "Ask about my work" box on my home page works the same way.

Also built

An AI step in code review: Gemini prompts that flag code smells, vulnerabilities and standards issues before merge, which reduced defects. I use AI every day to explore ideas, prototype and review code.

What I learned

Stakeholders understood the idea in minutes once they could see it working. A working prototype answers questions a slide deck only raises.

A subscription dashboard people can read at a glance, on any screen

Company
T-Mobile
Role
Front end and services
Stack
React, Redux, Jest, Spring Boot
Result
40% higher user satisfaction

Customers used the subscription dashboard to manage plans, check usage and handle billing. I designed and built its front-end components in React and Redux, with responsiveness and accessibility as the priority, and built the services behind them.

The problem

The dashboard had to work just as well on a phone as on a desktop, and be usable by everyone, including people using a keyboard or screen reader.

What I did

  • Designed and built the dashboard's front-end components in React and Redux, validated with Jest unit tests.
  • Worked with product managers and QA in Agile sprints to turn requirements into designs, and led code reviews.
  • Built the Spring Boot services for subscription activation, usage tracking and billing, with Kafka for real-time activity and notifications.

Design decisions

  • Usage first. What people check most sits at the top, as a number and a bar.
  • One layout, every screen. Cards reflow from three columns to one without hiding anything.
  • Warnings in words, not just color. "Near limit" is written out, so it doesn't rely on color alone.

Results

User satisfaction rose 40% through better responsiveness and accessibility. On the services side, query optimization and schema changes cut query time by 20%.

Shop flows for a family of prepaid brands

Company
TracFone Wireless
Brands
Straight Talk, TracFone and others
Stack
Java, Spring, REST/SOAP, SQL
Result
30% faster queries

TracFone runs several prepaid brands, including Straight Talk, for both consumers and business customers. I worked on the shop flows customers use to pick a phone and a plan, and on the services behind them.

The challenge

Several brands and customer types, B2B and B2C, share the same underlying flow. Each change had to work for all of them.

What I did

  • Worked on shop flows for Straight Talk, TracFone and their other B2B and B2C brands.
  • Built Spring MVC applications with SOAP and REST services, and turned 20+ user stories into system designs with a Scrum team.
  • Rewrote slow SQL queries after analyzing execution plans, and added 100+ unit tests with JUnit and Mockito.
  • Streamlined CI/CD with Jenkins and Docker.

Results

  • 30% better database efficiency from rewriting slow queries.
  • 30% fewer post-deployment issues after adding thorough tests.
  • 95% on-time delivery for key features, with 10% faster deployments.

What I learned

When one flow serves many brands, the shared parts have to be solid and the brand-specific parts have to be easy to change. That idea shaped how I build component libraries today.
